Annotationer

Vad annotationerna gör

Innan vi ser koden – här är de annotationer som dyker upp i alla tester.

@ExtendWith(MockitoExtension.class)

Sätts på testklassen. Aktiverar Mockito så att @Mock och @InjectMocks fungerar. Utan den händer ingenting när du annoterar fälten.

@Mock

Skapar ett falskt objekt av klassen. Alla metoder returnerar null eller 0 som standard. Du styr vad de returnerar med when(...).thenReturn(...). Ingen riktig databas, inga riktiga anrop.

@InjectMocks

Skapar ett riktigt objekt av klassen och stoppar in alla @Mock-fält i den via konstruktorn. Det är det här objektet du faktiskt testar.

@MockBean

Används i Spring-tester (t.ex. med @WebMvcTest). Fungerar som @Mock men registreras i Spring-kontexten så att controllern kan få den injicerad.

@WebMvcTest(X.class)

Startar bara webb-lagret – bara controllern du anger laddas. Service och repository laddas inte. Snabbare än att starta hela applikationen.

@Test

Markerar att en metod är ett test. JUnit hittar och kör alla metoder med den här annotationen automatiskt. Utan den ignoreras metoden.

Enhetstest

BookService – hämta en bok

Testar service-lagret i isolation. Repository är mockat – ingen databas körs.

BookServiceTest.java ENHETSTEST 
@ExtendWith(MockitoExtension.class)
class BookServiceTest {

    @Mock
    private BookRepository bookRepository;   // falskt repo, ingen databas

    @InjectMocks
    private BookService bookService;           // riktig service med mockat repo

    @Test
    void getById_returnsDto_whenBookExists() {
        // Arrange
        Book book = new Book("Brott och straff", "Dostojevskij", true);
        book.setId(1L);
        when(bookRepository.findById(1L)).thenReturn(Optional.of(book));

        // Act
        BookDto result = bookService.getById(1L);

        // Assert
        assertEquals("Brott och straff", result.getTitle());
        assertEquals("Dostojevskij", result.getAuthor());
        assertTrue(result.isAvailable());
    }

    @Test
    void getById_throwsException_whenBookNotFound() {
        when(bookRepository.findById(99L)).thenReturn(Optional.empty());

        assertThrows(RuntimeException.class,
            () -> bookService.getById(99L));
    }
}
Enhetstest

LoanService – låna ut en bok

Affärsregeln: en bok som inte är tillgänglig kan inte lånas ut. Testet kontrollerar båda fallen.

LoanServiceTest.java ENHETSTEST 
@Test
void checkOut_setsBookUnavailable_whenBookIsAvailable() {
    Book book = new Book("Brott och straff", "Dostojevskij", true);
    Borrower borrower = new Borrower("Anna Svensson");
    book.setId(1L);
    borrower.setId(2L);

    when(bookRepository.findById(1L)).thenReturn(Optional.of(book));
    when(borrowerRepository.findById(2L)).thenReturn(Optional.of(borrower));
    when(loanRepository.save(any())).thenAnswer(i -> i.getArgument(0));

    LoanDto result = loanService.checkOut(1L, 2L);

    assertFalse(book.isAvailable());       // boken är nu utlånad
    assertNotNull(result.getLoanDate());   // ett lånedatum sattes
}

@Test
void checkOut_throwsException_whenBookNotAvailable() {
    Book book = new Book("Brott och straff", "Dostojevskij", false); // ej tillgänglig
    book.setId(1L);
    when(bookRepository.findById(1L)).thenReturn(Optional.of(book));

    assertThrows(IllegalStateException.class,
        () -> loanService.checkOut(1L, 2L));
}
Integrationstest

BookController – testa endpoints

Startar webb-lagret med @WebMvcTest. Inga riktiga databasanrop – service är mockad.

BookControllerTest.java INTEGRATIONSTEST 
@WebMvcTest(BookController.class)
class BookControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockBean
    private BookService bookService;

    @Test
    void getAll_returns200_withListOfBooks() throws Exception {
        List<BookDto> books = List.of(
            new BookDto(1L, "Brott och straff", "Dostojevskij", true),
            new BookDto(2L, "Möss och människor", "Steinbeck", false)
        );
        when(bookService.getAll()).thenReturn(books);

        mockMvc.perform(get("/books"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.length()").value(2))
            .andExpect(jsonPath("$[0].title").value("Brott och straff"));
    }

    @Test
    void create_returns201_withNewBook() throws Exception {
        BookDto created = new BookDto(3L, "Röda rummet", "Strindberg", true);
        when(bookService.create(any())).thenReturn(created);

        mockMvc.perform(post("/books")
            .contentType(MediaType.APPLICATION_JSON)
            .content("{\"title\":\"Röda rummet\",\"author\":\"Strindberg\",\"available\":true}"))
            .andExpect(status().isCreated())
            .andExpect(jsonPath("$.id").value(3));
    }
}
Buggen som testet fångar

En oskyldig ändring som går fel

Du refaktorerar toDto() i BookService. Applikationen startar. Postman svarar. Allt ser bra ut.

Innan – korrekt 
private BookDto toDto(Book book) {
    return new BookDto(
        book.getId(),
        book.getTitle(),
        book.getAuthor(),
        book.isAvailable()  // ← rätt
    );
}
Efter – buggen introducerad 
private BookDto toDto(Book book) {
    return new BookDto(
        book.getId(),
        book.getTitle(),
        book.getAuthor(),
        false              // ← hårdkodat råkade stå kvar
    );
}

Alla böcker rapporteras nu som utlånade – oavsett om de finns på hyllan. En kund söker en ledig bok och hittar ingenting. Ingen kompileringsfel. Ingen stack trace.

Teststrategi

Vad är värt att testa?

Du behöver inte testa allt. Fokusera på det som faktiskt kan gå fel och kosta dig något.

✅

Affärslogik och regler

Kan en bok lånas ut om den inte är tillgänglig? Vad händer om låntagaren inte finns? Det är logik som kan brytas vid varje ändring.

✅

Felhantering – vad händer när något saknas?

getById(99L) när boken inte finns – kastar den rätt undantag? Returnerar controllern 404?

✅

Mappningslogik

Att alla fält hamnar rätt i DTOn är enkelt att råka förstöra vid refaktorering – och enkelt att testa.

⏭️

Trivial kod utan logik

En getter som returnerar ett fält, en konstruktor som sätter värden. Inget som kan gå fel – inget att testa.

AI-genererade tester

Vad AI behöver för att hjälpa dig

AI skriver bra tester om den har rätt kontext. Skickar du för lite – får du tester som inte kompilerar.

1

Klassen du vill testa

Hela källkoden. Metodnamn, returtyper och parametertyper måste stämma för att assertions ska fungera.

2

Beroendena

Vilka repositories eller services injiceras? AI:n behöver veta vad som ska mockas och vilka metoder de har.

3

DTO- och entitetsklasserna

Getters och fältnamn måste matcha. Annars skriver AI:n getName() när metoden heter getTitle().

4

Vilken typ av test

Enhetstest med Mockito? Controller-test med MockMvc? Säg det explicit – annars gissar AI:n.

Det du fortfarande måste göra själv

AI skriver testkod. Du bestämmer vad som är värt att testa – och om testerna faktiskt fungerar.

🔴

Kontrollera att testet KAN misslyckas

Ändra ett korrekt värde i koden till något fel. Blir testet rött? Annars testar det ingenting.

🧠

Välj vad som ska testas – inte AI:n

AI täcker det du ber om. Kantfall, affärsregler och felscenarier som är viktiga för ditt system – det vet bara du.

🔧

Räkna med att behöva justera

AI kan gissa fel metodnamn eller använda fel annotation. Läs igenom och kompilera alltid innan du litar på resultatet.

📈

Börja med det viktiga, inte det enkla

Testa affärslogiken och felhanteringen först. Triviala getters sist – eller inte alls.
